# Research Brief: Efficient PR Tracking in Desktop (Local) Agent Sessions

- **Date:** 2026-10-04
- **Requested by:** Engineering Manager (dispatch), for human/Architect review
- **Status:** Findings and a recommendation only. No plan, ADR, or implementation exists. Nothing here is approved. The Feature decomposition in section 9 is a sketch for review, not a plan.
- **Question:** How can a desktop (local) Claude Code session learn that a PR changed state (CI finished or failed, review or comment posted, merge conflict, merged) and be woken to react, at low token and context cost, without human prodding, replicating the cloud `subscribe_pr_activity` experience? Which options also help Kiro or Copilot desktop sessions?

Evidence labels: **verified** = read in official docs or this repo during this research (linked); **inference** = my reasoning from verified facts; **UNVERIFIED** = not confirmed, must be checked before relying on it. Fetch tools return model-written summaries of pages, not verbatim text, so wording-sensitive claims are flagged where it matters. Token figures are order-of-magnitude estimates (inference), not measurements.

---

## 1. Summary and headline answer

1. **No official local equivalent of `subscribe_pr_activity` exists** in the Claude Code docs I could fetch. The nearest first-party primitive is **Channels** (an MCP server pushes events into a running local session), which is a research preview and needs a launch flag. Third-party channel and PR-monitor projects exist (search snippets only, not evaluated; see section 8).
2. **The cheapest reliable pattern is a non-LLM "snapshot-diff" watcher** that polls GitHub with conditional requests through `ai-git`, compares against a persisted last-acknowledged snapshot, and prints nothing unless a PR changed. Idle cost is zero model tokens; a change costs one short digest line per PR.
3. **That one watcher can be delivered through several wake paths**, chosen by availability: a backgrounded wait-for-change command (works on every provider), the Monitor tool, a Channel (target state), hooks (catch-up on resume), or `/loop` (last resort). Building the watcher once and keeping the wake path swappable is the main design lever.
4. **Snapshot-diff beats webhooks for this use case** because a laptop sleeps and GitHub does not redeliver failed webhook deliveries automatically (verified), whereas a level-triggered diff naturally catches up on wake. Merge-conflict state also has no dedicated event, so a poll of PR mergeable state is needed regardless (inference; see section 5).
5. **Only the main session can own the watcher.** Background commands started by a subagent notify that subagent, and monitors die with it (verified), mirroring the cloud finding that subagent subscriptions wake only the parent.
6. **Kiro and Copilot:** the watcher and its inbox file are harness-neutral; the wake is not. On those harnesses the watcher is only useful if the agent runs it at checkpoints (pull), which is still cheap.

## 2. Local prior art checked first

- `docs/research/tool-tiers-and-harness-parity.md`: Kiro and Copilot have no agent-callable subscribe or schedule tool; PR follow-through is a platform feature there (Copilot `@copilot`, Kiro autonomous agent). Cloud tools are Claude-only.
- `docs/plans/features/AIF-010/verification-guide.md`: cloud PR events arrive as queued notifications read via `ReadNotifications`; only the most recent subscriber to a PR receives events; subagents share the parent session, so a subagent's subscription is the parent's.
- `docs/decisions/0007-harness-neutral-platform-tool-groups.md` (accepted): platform-provided tools are granted through capability-named harness-neutral groups resolved per adapter; unsupported groups are dropped and reported. Any new tool grant for the Engineering-Manager (for example Monitor) must go through this mechanism, not a Claude-specific yaml entry.
- `skills/pr-stewardship/SKILL.md`: poll-based, one check-and-act pass per invocation, "does not loop or sleep"; whoever dispatches decides re-invocation cadence. This brief fills exactly that missing "who re-invokes, and when" layer locally.
- `bin/ai-git.js`: wraps git and `gh` with the bot identity; subcommands `gh-<subcommand>` and `gh-api` (REST). Locally GraphQL-backed `gh pr ...` works; in cloud it is blocked (skill cloud table).
- No existing decision or arc42 section answers local PR tracking, so this is a fresh question.

## 5. Option space and evaluation

### 5.1 Options

- **A. `/loop` / `ScheduleWakeup` / `CronCreate` polling a PR check prompt.** Every tick is a full model turn.
- **B. Background Bash "wait-for-change"** running a non-LLM watcher that exits when any tracked PR changes (or at a timeout); the exit notification wakes the main session; the agent handles it and re-arms.
- **C. Monitor tool** running the same watcher in streaming mode (one line per change), re-armed on the deadline notice.
- **D. Plugin-declared monitor** auto-starting the watcher with the session.
- **E. Channel (custom MCP server)** that does the polling internally (like the Telegram plugin polls its platform) or receives webhooks, and pushes events; can also expose `watch_pr` / `unwatch_pr` tools mirroring the cloud API shape.
- **F. Hooks.** (F1) SessionStart and UserPromptSubmit inject a digest read from the watcher's inbox file (catch-up and next-turn delivery). (F2) `asyncRewake` command hook running the watcher and exiting 2 on change.
- **G. Webhook plus local relay** (smee.io, ngrok, cloudflared, `gh webhook forward`) feeding a local listener, then any of B to F as the delivery leg.
- **H. GitHub Notifications API** as a single cheap "something changed" trigger across all PRs, with a follow-up fetch for details.
- **I. `gh pr checks --watch`** per PR for CI only.
- **J. GitHub Actions that push or comment back.** Relay-style (workflow posts to a public topic the laptop subscribes to) or a PR comment/label.
- **K. Sidecar daemon plus `claude -p --resume`** (or Agent SDK host) re-invoking the agent per event.
- **L. Desktop scheduled task or cloud routine** starting a fresh stewardship session.
- **M. GitHub MCP server** as the watcher.

### 5.3 Per-option notes that drive the recommendation

- **Why not A as the primary:** it is the only option that spends model tokens when nothing happened. The docs themselves point from polling toward Channels or Monitor for this reason. It remains a valid fallback because it works on any provider and needs no code.
- **Why snapshot-diff (B, C, E share it):** a webhook stream is edge-triggered: events missed while the laptop sleeps are lost unless redelivered by hand (verified). A watcher that compares "current PR state" to "last acknowledged state" is level-triggered and self-heals after sleep, session restart, or a crash. It also covers merge-conflict state, which is a property of the PR plus its base branch rather than a PR event (inference; the dedicated webhook for it was not verified).
- **Digest, not content:** the watcher should emit PR number, change type (CI passed, CI failed with check names, review state, new comment count, mergeable state, merged or closed), actor login, and URLs, never comment bodies. This minimizes tokens and shrinks the prompt-injection surface: the channels docs describe an unfiltered inbound path as an injection vector, and PR comment text is attacker-controlled on any repo that accepts outside comments. The agent then fetches only the bodies it chooses to via `ai-git`. Optionally filter by actor allowlist (collaborators, the human owner) at the watcher.
- **Rate-limit arithmetic (inference):** a PR needs roughly 3 to 5 GETs per tick (PR object, check-runs for head SHA, reviews, review comments, issue comments). Repo-level list endpoints with `since` filters reduce this to a handful per repo regardless of PR count. At one tick per 60 s for 10 PRs, naive per-PR polling is 1,800 to 3,000 requests/hour; mostly 304s that do not count against the 5,000/hour primary limit (verified for correctly authorized conditional requests), but ETag support per endpoint must be checked and the secondary-limit treatment of 304s is unverified. Prefer repo-level lists and the Notifications API as an optional "something changed" gate if the bot PAT is classic.
- **Notifications API (H) caveats:** classic PAT only; delivery depends on the bot account's participation in PRs it authored or reviewed; the semantics of `ci_activity` (which runs trigger it) were not verified. Use it as an optimization hint, never as the only source of truth.
- **Subagents:** the main session must start the watcher. A watcher started by a subagent notifies that subagent (verified), and a Monitor started by a subagent stops with it (verified). The EM prompt and skill should state this explicitly. Local session concurrency has no "most recent subscriber" rule; two local sessions each running a watcher would both report (inference). Give the watcher a consumer ID and per-consumer acknowledgement state.
- **Windows:** Monitor needs Git Bash on Windows (verified); the repo is developed on Windows. A Node script launched through the shell avoids shell-script portability problems (inference).
- **Permissions:** background and Monitor commands are subject to the session's permission rules; an allow rule scoped to the watcher command is needed to avoid stalls (inference from permission-rule docs referencing Monitor). Agents are barred from raw `git`/`gh`, so the watcher must go through `ai-git`.
- **Hooks as the catch-up layer (F1):** hooks cannot wake an idle session, but a SessionStart hook injecting a pending-events digest handles "I closed the laptop and resumed." A UserPromptSubmit or Stop hook delivers events at the next natural boundary at near-zero cost. Hooks live in settings, not agent yaml, so how the framework would install them per harness is an open design point.
- **Kiro and Copilot:** the prior research found no agent-callable subscribe, schedule, or wake on either. The watcher script, the state file, and the digest format are harness-neutral. The pull path (the EM skill calls the watcher at checkpoints: before dispatching a wave, when a Task returns, at session start) works wherever the agent can run a shell command. Hook equivalents on Kiro and Copilot CLI are **UNVERIFIED** (not researched here); the Kiro IDE ignoring an agent's hooks field is a report in the earlier brief, not confirmed.

## 6. Recommended design

Not requested as a single pick by the dispatcher beyond "recommended design", so this is one recommendation with rationale; the alternatives are in section 7.

### 6.1 Shape

1. **Core: `pr-watch`, a non-LLM snapshot-diff watcher** (Node, matching the repo's existing `bin/` and `lib/` stack). Inputs: a set of PRs (owner/repo/number) registered in a small state file. It polls through `ai-git` using conditional requests, keeps per-PR ETags and a last-acknowledged snapshot, and prints a compact digest of differences. Modes: one-shot (print changes, exit), wait (block until any change or a timeout, then exit), stream (print a line per change). Registration and acknowledgement are explicit operations so the agent can mirror the cloud `subscribe` / `unsubscribe` semantics. Keep pure logic (diffing, digest formatting) separate from I/O per the testability rule.
2. **Wake path, in preference order, selected at runtime by the EM skill:**
   1. Native cloud tools if present (`subscribe_pr_activity`), unchanged.
   2. Local: backgrounded wait mode (option B) as the default, because it needs no new tool grant beyond shell, works on every provider, and has no 5 to 30 minute watch deadline beyond its own chosen timeout (30 minutes default for background commands, up to 2 hours; verified). Monitor stream mode (C) as the alternative where the tool is available, since it avoids re-arming after each event.
   3. Fallback: `/loop` self-paced running one-shot mode, accepting per-tick token cost.
3. **Catch-up layer:** a SessionStart hook (and optionally UserPromptSubmit) that runs one-shot mode and injects the digest, so resuming after sleep or a restart surfaces missed changes.
4. **Skill contract:** extend or complement `skill/pr-stewardship` / `skill/task-orchestration` so "register PR after creation, handle digest by running one stewardship pass for that PR, acknowledge, re-arm the wait" is a documented loop, and degrade to checkpoint polling when no wake path exists (the pull path for Kiro and Copilot).
5. **Target state, gated on an ADR:** wrap the same engine as a **Channel** MCP server under `servers/` that exposes `watch_pr` / `unwatch_pr` tools and pushes digests, giving the closest experience to `subscribe_pr_activity` (no re-arm, push into the idle session). It depends on a research-preview feature, a launch flag with a confirmation dialog on every start, and an org setting on Team/Enterprise, so it should follow, not lead.

### 6.2 Rationale

- Zero model tokens while idle; tens of tokens per change plus one handling turn, the same cost shape as cloud wakes.
- Level-triggered, so sleep, crashes, and restarts do not lose events (webhooks do; verified no auto-redelivery).
- Outbound polling only: no public ingress, no webhook admin rights, no relay account, no inbound listener to secure.
- Reuses the existing auth path (`ai-git` bot PAT) and the existing `ai-git gh-api` REST surface that already works in both cloud and local sessions.
- One engine, many wake paths: swapping B for C or E later does not change the skill contract or the state model.
- Harness-neutral core; only the wake step is Claude-specific, which is consistent with ADR 0007's direction.

### 6.3 Cheapest viable first step

Build the one-shot and wait modes of `pr-watch` for a single PR, with a small spike test on a desktop session answering the three UNVERIFIED wake questions: (a) does a backgrounded wait command's completion wake an **idle** main session; (b) does a Monitor stream line do so; (c) does the EM agent definition's tool allowlist need extra entries (Monitor, any task-output tool) for these to be callable. Mirror the structure of the AIF-010 verification guide. Without the (a) result, option B's "no prodding" claim is unproven; if (a) fails, C or F2 becomes primary.

| Idle-wake from background command does not work                         | Monitor stream (C); then `asyncRewake` hook (F2) if its re-arm behavior is confirmed                                                   |
| Provider without Monitor (Bedrock, Vertex, Foundry, telemetry disabled) | Backgrounded wait mode (B), or `/loop` one-shot polling (A)                                                                            |
| Need push latency under about 10 s                                      | Webhook plus relay feeding a Channel (G + E); needs repo/org webhook rights and an ADR                                                 |
| Notifications API usable (classic PAT acceptable)                       | Add H as a cheap gate in front of the per-PR requests                                                                                  |
| No session open at all (unattended)                                     | Sidecar daemon plus `claude -p --resume` (K), only for sessions that are not live; or a cloud routine for the PR-opened event only (L) |
| Kiro or Copilot desktop                                                 | Pull mode at checkpoints; Copilot `@copilot` and Kiro autonomous agent remain the platform routes per the earlier brief                |

## 8. Risks and open questions

**Risks**

- **Preview and flag drift:** Channels and Monitor may change; the channels docs say flag syntax and contract may change. Keep the engine independent of the transport.
- **Prompt injection through PR text:** even digest-only events leave the agent to fetch bodies; stewardship passes must treat bodies as data. An actor allowlist at the watcher is a cheap mitigation.
- **Silent watcher death:** a dead background process looks like "no changes." Needs a heartbeat or last-successful-poll timestamp that the EM checks at checkpoints.
- **Re-arm loops and noise:** a flapping check or an automated bot commenting repeatedly can cause runaway wakes (the earlier brief names runaway re-arming as a cloud risk too). Debounce and a per-PR event cap in the watcher.
- **Duplicate consumers:** parallel local sessions on one machine each get the same event; needs consumer-scoped acknowledgement.
- **Token scope:** the Notifications API needs a classic PAT, which may be broader than the bot's current token. Do not widen bot scope without a security decision.
- **Third-party projects** (claude-beacon, a GitHub-channels plugin, PR-monitor skills) surfaced only as search snippets ([glama.ai claude-beacon](https://glama.ai/mcp/servers/drmf-cz/claude-beacon), [claudefa.st Monitor guide](https://claudefa.st/blog/guide/mechanics/monitor)); they were not fetched or reviewed. Do not adopt without a review of their code and permissions. No instructions found in fetched content tried to direct this research.

**Open questions (UNVERIFIED, each testable)**

1. Does completion of a backgrounded command wake an idle main session? Same for Monitor lines.
2. Does the 30-minute Monitor cap apply to plugin monitors?
3. Can an `asyncRewake` hook be re-armed, and is its timeout enforced?
4. Which GitHub GET endpoints return usable ETags (PR, check-runs, reviews, both comment endpoints, repo-level `since` lists), and do 304s consume secondary-limit points?
5. Is the bot PAT classic or fine-grained, and is a classic token acceptable for the Notifications API?
6. What exactly triggers `ci_activity` for a bot account that authored the PR?
7. What does the Engineering-Manager agent's installed `tools:` allowlist need so Monitor and background output are callable on desktop? (In cloud, the allowlist silently blocked tools; see the earlier brief.)
8. Do background tasks and Monitor survive a context compaction and a `--resume`? Docs say background Bash and monitor tasks are never restored on resume (verified), so a resume must re-register; confirm compaction behavior.
9. Webhook rights: can the bot create repo or org webhooks, or must a human?
10. Kiro and Copilot: hook support, and whether any CLI can run a periodic script that injects a message.

## 9. What needs an ADR versus ordinary implementation

**Genuine forks (Architect ADR, human approval):**

1. **Delivery transport and dependency on a research-preview feature:** adopt Channels as the framework's standard push transport (launch flag, dev-flag dialog, org enablement, claude.ai or Console auth only), versus staying on backgrounded commands and Monitor. Costly to reverse once agent prompts and install flow assume it.
2. **Sidecar daemon or not:** whether the framework ever ships a persistent local process (webhook listener, relay client, or `claude -p --resume` re-invoker) versus only session-scoped watchers. This changes install footprint, security surface, and lifecycle ownership.
3. **Webhook ingress:** whether to introduce any public ingress or third-party relay, and under whose account and secret handling.
4. **Token scope widening** (classic PAT for Notifications) if proposed.

**Ordinary implementation (inside existing decisions):**

- The `pr-watch` engine, state file, digest format, tests, and its `ai-git` integration.
- EM and stewardship skill text to register, wait, handle, acknowledge, and re-arm; graceful degradation when no wake path exists (consistent with the earlier brief's conclusion 5).
- Granting Monitor or other native tools to the EM through the harness-neutral group mechanism already decided in ADR 0007 (naming a new group is an implementation detail of that ADR; revisit only if the group naming is contested).
- SessionStart or UserPromptSubmit digest hook, once the install path for hooks is settled.
- arc42 §5.02 update (harness adapters) and a new building-block section for the watcher, per the Doc-Update Acceptance Gate.

## 10. Rough suggested Feature decomposition (for review only)

1. **Spike and verification (first):** answer open questions 1, 3, 4, 7 on a desktop session with a throwaway PR; produce a verification guide in the AIF-010 style. Output decides whether B or C is primary.
2. **`pr-watch` engine:** pure diff and digest modules; REST client via `ai-git gh-api` with conditional requests; per-PR and consumer-scoped state; one-shot, wait, and stream modes; debounce and event caps; heartbeat; fixture-based unit tests; integration test with a fake GitHub.
3. **Skill and EM integration:** register and unregister steps, handle-digest loop, "main session only" rule, degradation to pull mode; tool or group grants through ADR 0007 mechanics; update `skill/pr-stewardship` and `skill/task-orchestration` references.
4. **Catch-up hooks:** SessionStart and UserPromptSubmit digest injection, with the framework install path for hooks decided first.
5. **Harness parity notes:** document the pull-mode path for Kiro and Copilot; verify hook equivalents there.
6. **Optional, ADR-gated:** Channel MCP server under `servers/` wrapping the engine, with sender gating and `watch_pr` / `unwatch_pr` tools; notifications-API gate if token scope is approved.
7. **Docs:** arc42 section for the watcher and update §5.02; research brief follow-up with measured token and request counts from the spike.
