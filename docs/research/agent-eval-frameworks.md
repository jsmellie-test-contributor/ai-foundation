# Research Brief: Third-Party Frameworks for Testing/Evaluating LLM Agent Behavior

**Date:** 2026-09-27
**Requested by:** Engineering Manager / Software-Engineer (process-model validation follow-up)
**Question:** Should `ai-foundation` adopt a third-party LLM-eval framework for its planned agent-behavior
test category, or build it in-repo with `node:test` (mechanical checks) plus a Principal-Engineer dispatch
(judgment checks)?

## Prior art checked

- `docs/decisions/` (flat MADR numbering 0001-0006, plus an `archive/` of older decision records): no
  ADR numbered 0007 exists, and none of 0001-0006 addresses test-runner choice or agent-eval tooling.
  `docs/decisions/0006-plain-js-with-jsdoc.md` is the closest — it settles plain JS + JSDoc + `tsc
--noEmit`, not test-runner choice.
- `docs/architecture/02_constraints.md`'s "undocumented decisions" table explicitly lists `node:test`
  over Jest/Vitest/Mocha as a **real but not-yet-recorded** decision — evidenced by none of the three
  appearing in `package-lock.json`. So the "existing convention" the dispatcher asked about is confirmed
  real (`package.json`'s `test` script runs `node --test "**/*.test.js"`, and all 37 files under
  `tests/unit|integration|validation` are `node:test`), but it is not yet an ADR. This brief treats it as
  an established-but-unratified convention, not a settled ADR — the dispatcher's premise ("if it still
  exists") does not hold; there is no 0007 to check against, only the gap noted above.
- `docs/plans/process-model-test-plan.md` — the validation pass that motivated this research. Its
  "Deliverable"/Finding B1 already establishes the concrete gap: nothing today checks agent _output_
  against behavioral rules (word budgets, banned content, escalation behavior), only file schema
  (`tests/validation/schemas.test.js`, `refs.test.js`).

No existing decision answers this question — proceeding with fresh research.

**Cross-cutting pattern:** every framework surveyed is built around grading **one model call's output against a reference or rubric** (a chat completion, a RAG answer). None models "dispatch a multi-agent pipeline, let it run for real wall-clock time across several tool calls and git commits, then check the resulting repo state (files, frontmatter, commit ordering, word counts) plus the transcript." That shape — this repo's actual need, per `docs/plans/process-model-test-plan.md`'s own findings — is closer to an integration test with an LLM-graded assertion bolted on than to a "prompt eval." The frameworks that are genuinely Node-native (promptfoo, autoevals) are libraries whose core value (rubric grading, `Score` objects) could be called from inside a `node:test` test if their scoring model were wanted; the frameworks whose design center is closest to this repo's actual need (Inspect AI, and to a lesser extent DeepEval's LLM-as-judge metrics) are Python-only for the parts that matter.

## (b) Fixture/sandbox lifecycle management for repeated agent-dispatch tests

Searched specifically for tooling purpose-built to spin up/reset a disposable git+GitHub sandbox repeatedly
for agentic pipeline testing (the exact thing `process-model-test-plan.md`'s Validation Report did by hand
this session, against `jsmellie/placeholder` and two `git worktree` checkouts).

- **SWE-bench and its harness family** (SWE-bench, SWE-smith, R2E-Gym, Multi-SWE-bench,
  [SWE-bench/SWE-bench](https://github.com/SWE-bench/SWE-bench)): containerized (Docker) evaluation
  harnesses, but built around a fixed benchmark shape — a frozen repo snapshot at a specific commit, a
  known GitHub issue, and a single generated patch checked against a hidden test suite. There is no
  human-in-the-loop approval gate, no multi-agent-role pipeline (Architect → EM → SE → PE), and no git
  _history_ assertion (commit ordering, `Approved`-status commit existing before implementation) — the
  unit under test is a patch diff, not a process.
- **Generic agent-sandbox infrastructure** (e.g. `sandboxio`, Railway's agent sandboxes, `ephemeral-sandbox`
  projects found on GitHub): these provision isolated _execution_ environments (containers, snapshots,
  teardown) for a single agent's code-execution tool calls. They solve "give one agent a disposable
  filesystem/shell safely," not "provision a disposable GitHub repo with branch protection/PR/CI wired up,
  dispatch five different agent roles against it in sequence, and assert on the resulting commit graph."
- **Conclusion:** nothing found is purpose-built for this repo's actual shape of test (multi-role pipeline
  dispatch against a real or realistic git+GitHub remote, graded on process conformance rather than patch
  correctness). The closest match to what's actually needed is what the manual validation pass already
  did by hand: `aif init` a throwaway project repo (or use an isolated `git worktree` of `ai-foundation`
  itself for framework-repo scenarios), let `ai-git`/`gh` operate against a real disposable GitHub repo,
  and tear it down after. That is scriptable in plain Node (`child_process` + the CLI's own `aif`/`ai-git`
  commands) without a third-party dependency; no framework surveyed would remove meaningful work from that
  script, since none of them know this repo's own plan-lifecycle/state-schema/skill vocabulary to assert
  against — that logic has to be hand-written regardless of which sandboxing layer runs underneath it.

## (c) Recommendation

**Do not adopt a third-party eval framework. Build the mechanical half in `node:test` (this repo's
established pattern, `tests/agent-behavior/` alongside `unit`/`integration`/`validation`) and the
judgment half by dispatching Principal-Engineer as grader, reusing `skill/code-review`/
`skill/review-severity`'s existing severity taxonomy and Review Report shape rather than a new tool.**

Rationale:

1. **No framework surveyed fits the actual unit under test.** Every LLM-eval framework in section (a) is
   architected around grading a single model response against a rubric or reference answer. This repo's
   need — as `process-model-test-plan.md`'s own Finding B1 states directly — is to check a _committed
   artifact plus git history_ against a checklist (word budget, banned-vocabulary, frontmatter schema,
   commit ordering, absence of code in an ADR body). The mechanical half of that is a solved problem in
   plain Node already (`tests/validation/schemas.test.js`, `terminology-sweep.test.js`, and the CI guards
   Track D of the same plan exercised) — it needs more assertions in the same style, not a new framework.

2. **The two Node-native options (promptfoo, autoevals) would add a dependency that contributes little
   this repo doesn't already have.** `autoevals`'s value is "a `Score` object and a library of pre-written
   rubric prompts"; this repo would still have to author every rubric prompt itself (its rules are
   repo-specific — `steering/engineering/core.md`'s Hard rules, `skill/adr-authoring`'s word budget — no
   generic framework ships them), and dispatching Principal-Engineer directly (an agent that already
   reasons in exactly this repo's own severity/finding vocabulary via `skill/review-severity`) produces a
   structured, actionable Review Report for free, without introducing a second grading vocabulary
   (`Score` 0-1 + `reason` string) alongside the one `skill/review-severity` already owns
   (CRITICAL/HIGH/MEDIUM/LOW + actionable-finding template). Running both would mean every judgment check
   has two different report shapes to reconcile.

3. **The two options whose design center is genuinely closest (Inspect AI, DeepEval's LLM-as-judge
   metrics) are Python-only for the parts that matter**, in a repo whose one recorded language decision
   (`docs/decisions/0006-plain-js-with-jsdoc.md`) is explicitly "zero build step... every source file must
   run directly under Node," and whose `02_constraints.md` already flags `node:test`-over-Jest/Vitest/Mocha
   as a real, if unratified, convention. Adopting either means standing up a second language runtime, its
   own dependency manager, and (for Inspect AI) a sandboxing subsystem (Docker/K8s) purely to reach a
   feature set — rubric grading via an LLM call — that dispatching an existing agent already provides.

4. **This repo already has the exact organizational pattern a "judgment grader" needs, built and proven.**
   `skill/review-severity` supplies the severity taxonomy, blocking rule, and report template every
   domain review skill in this repo shares; `skill/code-review` already dispatches Principal-Engineer to
   apply domain-specific checks and hand findings to that shared skill. Judgment-based agent-behavior
   assertions (did the agent correctly refuse to fabricate a fact; did it escalate rather than decide
   unilaterally; are the options in a survey genuinely distinct) are the same shape of question
   Principal-Engineer already answers for code — a new skill (e.g. `skill/agent-behavior-review`) that
   feeds Principal-Engineer the transcript/artifact plus a checklist, and renders findings through
   `skill/review-severity` exactly like `skill/code-review` and `skill/ai-component-review` already do,
   is strictly less new machinery than bolting on a third-party framework's own scoring/reporting model
   alongside the one already in place.

5. **What this recommendation does _not_ rule out:** if a specific narrow gap emerges later — e.g.
   wanting many cheap, deterministic LLM-graded assertions run in bulk without a full Principal-Engineer
   dispatch's cost — `autoevals` (genuinely Node-native, a plain library, no platform account required) is
   the one option worth a second look at that point, called from inside a `node:test` test as one more
   assertion, not adopted as the harness itself. That is a "revisit if warranted" note, not part of this
   recommendation.
